CERBERUS SECURITY REPORT — OWASP Juice Shop
Target: <path>\juice-shop  ·  Runtime: http://localhost:3000

Risk: CRITICAL  ·  9 CRITICAL, 11 HIGH, 9 MEDIUM, 3 LOW (app-level, manually
      traced + runtime proven; excludes the 489-finding scanner haul detailed
      below)
App nature: OWASP Juice Shop — an intentionally-vulnerable training/CTF
            application. Every finding below is a deliberately planted
            vulnerability. This report is a validated attack map, not a
            surprise triage list.
Verdict: An unauthenticated attacker can fully take over any account
         (including admin) three independent ways — SQL injection, JWT
         algorithm confusion, or a leaked MD5 password hash — read or forge
         any other user's data (baskets, orders, reviews, coupons), run
         arbitrary JavaScript inside the database engine, and get free
         "deluxe" membership and free discount coupons. Every chain below
         was executed live against the running instance, not just read in
         source.

--- 1. JWT algorithm-confusion auth bypass (pre-auth admin takeover) · 🔴 CRITICAL · Confirmed exploitable ---
  Where:    lib/insecurity.ts:52 (isAuthorized), lib/insecurity.ts:189
            (updateAuthenticatedUsers)  (endpoint: any route behind
            security.isAuthorized(), e.g. GET /api/Users)
  Impact:   Full authentication bypass as ANY user, including admin, with
            zero credentials — worse than the SQLi below because it needs no
            valid account at all.
  Trace:
    1. publicKey = fs.readFileSync('encryptionkeys/jwt.pub')   lib/insecurity.ts:20
    2. -> served world-readable                                server.ts:296-297, routes/keyServer.ts:9-19
    3. -> expressJwt({ secret: publicKey })  (no `algorithms` allowlist)   lib/insecurity.ts:52
    4. -> jwt.verify(token, publicKey, callback)  (no options -> algorithm from token header)  lib/insecurity.ts:189
  Attack:
    1. GET /encryptionkeys/jwt.pub  -> 200, returns the RSA public key in plaintext
    2. Build token: header {"alg":"HS256"}, payload {"data":{"id":1,"role":"admin",...}},
       sig = HMAC-SHA256(header.payload, <public key bytes>)
    3. GET /rest/user/whoami with that token -> 200 {"user":{"id":1,"email":"admin@juice-sh.op"...}}
       GET /api/Users with that token -> 200 (admin-only user list)
       (verified against http://localhost:3000; zero real credentials used)
  Basis:    Static + runtime confirmed.
  Intentional: known challenge family (jwtChallenges)
  Fix:      expressJwt({ secret: publicKey, algorithms: ['RS256'] }); same for
            jwt.verify(token, publicKey, { algorithms: ['RS256'] }, cb).
            Also stop serving the raw PEM at a guessable public path.

--- 3. NoSQL $where JavaScript injection (server-side JS execution in DB engine) · 🔴 CRITICAL · Confirmed exploitable ---
  Where:    routes/showProductReviews.ts:36, routes/trackOrder.ts:18,
            routes/chat.ts:149  (endpoints: GET /rest/products/:id/reviews
            [no auth], GET /rest/track-order/:id [no auth], chat tool
            getProductReviews)
  Impact:   Arbitrary boolean/JS predicate injection into the marsdb query
            engine — data exfiltration across all records, and (per the
            underlying library's own advisory) command injection. The app
            even ships a global `sleep()` helper solely to let this be
            escalated to a DoS primitive (showProductReviews.ts:17-26).
  Trace:
    1. req.params.id (raw, only truncated to 40 chars when the
       "noSqlCommandChallenge" is enabled — the default)          routes/showProductReviews.ts:31
    2. -> db.reviewsCollection.find({ $where: 'this.product == ' + id })  routes/showProductReviews.ts:36  <- sink
  Attack:
    1. GET /rest/products/1/reviews -> 2 reviews (baseline)
    2. GET /rest/products/1%20%7C%7C%20true/reviews -> 29 reviews (all
       reviews, all products) — proves the `id` is evaluated as a JS
       expression, not compared as data (verified against
       http://localhost:3000)
  Basis:    Static + runtime confirmed. Corroborated by npm-audit CRITICAL
            "Command Injection in marsdb" (GHSA-5mrr-rgp6-x4gr).
  Intentional: known challenge (noSqlCommandChallenge / noSqlOrdersChallenge)
  Fix:      Never build $where from user input; query `{ product: Number(id) }`
            directly. Remove the global sleep() DoS helper. Upgrade off marsdb.

--- 4. Password hash disclosure via /rest/user/whoami?fields= + JSONP cross-origin leak · 🔴 CRITICAL · Confirmed exploitable ---
  Where:    routes/currentUser.ts:27-33 (field allowlist bypass),
            routes/currentUser.ts:54-58 (JSONP)  (endpoint: GET /rest/user/whoami)
  Impact:   Any authenticated user can dump their own MD5 password hash (and
            totpSecret/deluxeToken) via a query param, and — because the
            response also supports `?callback=`, bypassing same-origin
            protections — any third-party website can exfiltrate it
            cross-origin while the victim is logged in (classic JSONP leak,
            CSRF-equivalent).
  Trace:
    1. req.query.fields split on ',' with no allowlist check     routes/currentUser.ts:22-23
    2. -> baseUser[field] = user.data[field]  (full server-cached
       record incl. password/totpSecret)                        routes/currentUser.ts:29-31
    3. -> req.query.callback present -> res.jsonp(response)      routes/currentUser.ts:54-58  <- sink
  Attack:
    1. GET /rest/user/whoami?fields=password,totpSecret,deluxeToken
       -> {"user":{"password":"e541ca7ecf72b8d1286474fc613e5e45",...}}
    2. GET /rest/user/whoami?fields=password&callback=leak
       -> `/**/ typeof leak==='function' && leak({"user":{"password":"e541c..."}});`
       (executes cross-origin from any page that <script src="">'s this URL
       while the victim's session cookie is attached)
       (both verified against http://localhost:3000)
  Basis:    Static + runtime confirmed.
  Intentional: known challenge (passwordHashLeakChallenge / emailLeakChallenge)
  Fix:      Return only an explicit safe-field allowlist regardless of the
            `fields` param; remove JSONP support entirely.

--- 5. Hardcoded RSA private key, MD5 password hashing, hardcoded HMAC secret · 🔴 CRITICAL · Confirmed in code ---
  Where:    lib/insecurity.ts:21 (privateKey), lib/insecurity.ts:41 (MD5
            hash), lib/insecurity.ts:42 (hardcoded HMAC key)
  Impact:   Full JWT signing key is in source control (compounds finding 1);
            passwords are MD5 (trivially crackable, no salt); a static HMAC
            key ('pa4qacea4VK9t9nGv7yZtwmj') is reused app-wide for
            integrity checks.
  Trace:    Not applicable — plainly hardcoded in source, no request path needed.
  Attack:   Not performed beyond finding 1 (which already consumes this key).
  Basis:    Static confirmed. Corroborated by gitleaks (Private Key / Generic
            API Key rules hitting this exact file).
  Intentional: known challenge content (used across multiple challenges)
  Fix:      Load signing keys from a secret store, rotate off any
            source-controlled key; hash passwords with bcrypt/argon2 + salt;
            derive HMAC keys per-purpose from a managed secret.

--- 21. Missing Content-Security-Policy on API responses · 🟠 MEDIUM · Confirmed (ZAP) ---
  Where:    Every /rest/* and /api/* response
  Impact:   No CSP header on API/JSON endpoints; defense-in-depth gap for any
            XSS that does land (findings 8/9).
  Fix:      Add a restrictive CSP header via helmet.contentSecurityPolicy().

--- 22. CORS wildcard (Access-Control-Allow-Origin: *) on all endpoints · 🟠 MEDIUM · Confirmed (ZAP) ---
  Where:    app.use(cors())  server.ts:183, reflected on every route
  Impact:   Any origin can read API responses if a request is made
            cross-site (compounds finding 4's JSONP leak; also allows silent
            cross-origin reads of any endpoint that doesn't require
            state-changing methods).
  Fix:      Restrict CORS to known origins; never combine wildcard origin
            with credentialed endpoints.

--- 23. Absence of anti-CSRF tokens on state-changing forms · 🟠 MEDIUM · Confirmed (ZAP) ---
  Where:    /profile, /profile/image/file, /profile/image/url (form posts)
  Impact:   No CSRF token on profile-image and username-change forms;
            partially mitigated by Bearer-token auth on the JSON API but the
            cookie-based /profile forms are exposed.
  Fix:      Add CSRF tokens (or SameSite=strict cookies) to all state-changing
            form posts.
